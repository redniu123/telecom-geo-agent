# 片区通信设施批量接入设计与自动成册总体方案

> 文档版本：V1.0（评审稿）
> 编制日期：2026-09-06
> 对应赛题：XA-202610 子赛题 1“面向专业 GIS 平台的通信工程智能辅助设计”
> 目标系统：面向片区通信建设任务的批量接入规划、资源冲突处理与标准设计图册自动生成系统
> 当前状态：用户已于 2026-09-06 明确授权按 H0—H6 开发；H7 仍为可选且不得抢占核心交付
> 数据边界：真实公开 GIS 背景 + 派生候选走廊 + 合成通信设施与资源属性
> 成果边界：竞赛级智能辅助设计原型，不是运营商现网系统，不生成可直接施工或签章的正式施工图

## 1. 结论与立项建议

本方案技术可行、比赛价值明确，并且能够在现有竞赛版基础上增量实现，不需要推倒已经通过验证的单任务核心。

建议把现有“A 点到 B 点的一次线路设计”降级为底层回归样例，把比赛主场景升级为：

> 在一个真实公开 GIS 背景的城市核心片区内，批量导入一批待接入通信设施任务，按照固定优先级顺序，为每个任务完成拓扑规划、资源校核、动态资源预占、冲突绕行、异常分流、工程量汇总和标准设计图册生成。

本次升级解决的主要问题不是单条路线计算困难，而是设计人员面对数十条任务时，需要重复完成标点、选路、查资源、改路、制图、填表、汇总和成册。系统价值应通过“批量消化繁琐工作”和“只把例外留给人”体现。

综合时间、数据、安全和实现风险，推荐采用以下三档规模：

| 数据档位 | 空间与网络 | 任务规模 | 用途 | 是否比赛必做 |
|---|---|---:|---|---|
| A. 回归基线集 | 当前 79 节点、79 边、A/B 两点 | 3 个冻结单任务场景 | 保证现有能力不退化 | 是 |
| B. 主展示集 | 当前约 2.284 km² 公开背景，使用最大连通分量 411 节点、444 边 | 3 个合成汇聚机房、30 个待接入任务 | 现场演示、图册、人工对照实验 | 是 |
| C. 压力测试集 | 同一数据契约，可使用完整图或额外生成的非现实合成图 | 100 个批量任务 | 性能、稳定性、失败覆盖 | 是，但不要求逐页展示 |

因此，原建议中的“12—20 个任务”作为主展示规模偏保守，本方案将主展示目标提高到 30 个任务。面积暂不盲目扩大：当前 2.284 km² 的核心城区样板已经包含 2716 个建筑和足够的道路拓扑，人工工作量主要由任务数量、资源依赖和图纸数量决定。只有在主展示集稳定通过验收后，才考虑把公开 GIS 背景扩展到 5—10 km²；扩区不属于比赛必做门槛。

## 2. 赛题约束与方案定位

### 2.1 赛题直接要求

比赛文件对子赛题 1 的要求可以归纳为：

- 以 QGIS 等开源 GIS 平台为专业设计载体；
- 通过参数化输入、AI 辅助布局或低代码交互降低专业软件门槛；
- 面向基站、管线、机房等通信设施；
- 实现自动化拓扑设计、场景构建和标准图纸生成；
- 用真实、可核查的验证材料证明效果；
- 智能设计效率提升应达到 30% 及以上，或手工绘图操作减少 50% 以上；
- 不能只提交概念方案、静态图片或文字说明，必须有可运行成果和验证支撑。

本方案与上述要求的对应关系如下：

| 赛题要求 | 本方案对应能力 |
|---|---|
| 参数化输入 | 批量任务表、资源参数、优先级、禁用段、设计偏好 |
| AI/低代码交互 | 结构化表单为可靠入口；大模型仅生成受约束的参数草案 |
| 自动拓扑设计 | 多任务候选路径、约束校核、有限绕行 |
| 场景构建 | 公开 GIS 背景、合成设施、资源台账和约束图层 |
| 标准图纸生成 | 片区总览、逐任务 A3 页面、汇总表和异常页自动成册 |
| 效率提升 | 同起止边界的人工 QGIS 与系统批处理对照实验 |
| 真实性与可核查 | 原始输入、参数指纹、事件日志、输出哈希、录屏和人工基线 |

### 2.2 作品边界

本项目定位为“智能辅助设计”，而不是自动批准施工的无人设计系统。

系统可以：

- 批量生成候选设计；
- 自动执行明确、有限、可解释的规则；
- 自动处理可修复的资源冲突；
- 标记需要人工判断的异常；
- 生成竞赛级设计图册和工程量摘要；
- 保留从输入到输出的可复算证据。

系统不能在当前阶段声称：

- 已接入运营商真实机房、管道、光缆、管孔和占用数据；
- 已覆盖全部国家、行业、地方和企业规范；
- 已完成现场勘察、地下管线探测和施工可行性确认；
- 输出可以直接用于施工、签章、审计、招标控制价或竣工验收；
- 批量结果是全局数学最优；
- 大模型的自由文本结论可以覆盖工程规则。

## 3. 主场景的行业工作实质

### 3.1 场景名称

**城市核心片区通信设施批量接入设计与自动成册。**

### 3.2 业务背景

一个片区在新建、扩容或集中建设期间，可能同时形成多条接入任务。设计人员通常需要收集任务点、汇聚节点、道路和现有资源信息，逐条选择路由，检查容量或禁用状态，形成路线图、材料汇总和异常说明。条件变化后，还需要识别受影响任务并返工。

公开工程文件显示，通信线路与管道设计关注路由、距离、容量、局所方向、管道衔接和第二物理路由等内容；例如北京市公共资源交易服务平台公开的一份通信管线改移设计文件明确列出合理路由、管孔资源、不同入局方向、第二物理路由、管道容量和管道衔接等设计事项（<https://ggzyfw.beijing.gov.cn/cmsbj/u/cms/cn.gov.bjggzyfw.www/202512/2782145385376.pdf>）。公开的通信工程勘察计价文件则把收集资料、调查情况、选定路由、现场测量、定位和疑点核查列为通信管道及光电缆线路勘察工作内容（<https://www.yueyang.gov.cn/web/uploadfiles/202403/2024031115502241762.pdf>）。本项目只选择其中适合 GIS 原型验证的一段流程，不替代勘察和正式设计。

### 3.3 人工流程中的重复劳动

对每个任务，设计人员往往需要重复完成：

1. 从任务表读取设施编号、坐标、业务属性和目标机房；
2. 在 GIS 中定位或创建点；
3. 判断点是否落在可用网络附近；
4. 查找可连接的道路或候选通道；
5. 选择主路由；
6. 检查沿线状态、剩余资源和显式禁用段；
7. 遇到问题时删除或重画部分路线；
8. 重新统计路线长度；
9. 填写该任务的材料和资源占用；
10. 设置图层、标注、图例、比例尺和图幅；
11. 导出该任务图纸；
12. 把单任务结果合并到总表和图册；
13. 当资源状态变化时，找出受影响任务并返工。

单个任务并不一定复杂，但 30 个任务会形成数百次同类操作和数十页重复制图。系统的核心价值是把上述重复流程变成一次批量执行，并让人员只复核异常任务。

### 3.4 为什么不是“把单任务毫无变化地循环 30 次”

本方案接受批量循环本身就是重要价值，但增加一个最小、必要的跨任务关系：共享资源台账。

每一个成功任务会在其最终路线经过的通道段上预占资源，后续任务读取更新后的资源状态。因此：

- 任务顺序可以影响后续任务是否需要绕行；
- 高优先级任务先获得有限资源；
- 失败任务不能消耗资源；
- 同一批次重跑必须从相同的冻结基线开始，不能重复扣减；
- 系统需要解释“为什么这一任务改路，而前一任务没有”。

这个机制足以形成真实的跨任务复杂性，又不需要引入高风险的全局组合优化。

## 4. 比赛主展示场景定义

### 4.1 场景故事

> 某城市核心片区收到 30 条通信设施接入设计任务。设计人员需要将待接入设施连接到 3 个合成汇聚机房，优先利用候选已有通道，避开禁用或待核查路段，并在有限子管资源下按任务优先级完成规划。系统批量生成方案，对满管任务自动尝试一次改路，对无法自动决定的任务进入人工复核，最后形成片区总览、任务明细、资源占用、工程量汇总和完整设计图册。

### 4.2 主展示集规模

| 对象 | 建议数量 | 说明 |
|---|---:|---|
| 公开 GIS 覆盖范围 | 约 2.284 km² | 当前已审计上海普通城市街区样板 |
| 道路图节点 | 411 | 使用最大连通分量 |
| 候选通道路段 | 444 | 沿公开道路几何派生，不称为现实管道 |
| 合成汇聚机房 | 3 | 分布在最大连通分量的不同位置 |
| 待接入任务 | 30 | 主展示和人工对照对象 |
| 优先级 | 3 档 | 高、中、低；同档按 task_id 稳定排序 |
| 资源状态 | 至少 4 类 | 可用、接近满载、满管、禁用/待核查 |
| 结果状态 | 至少 4 类 | 直接成功、绕行成功、待人工复核、明确失败 |
| 图册页数 | 约 36 页 | 封面/总览/汇总 + 30 个任务页 + 资源/BOM/异常/边界页 |

### 4.3 任务结果分布要求

不在输入文件中写死最终路线，但主展示数据必须经过独立验收，确保至少覆盖：

- 多个无需修复的直接成功任务；
- 多个因本次批量预占导致的容量冲突；
- 多个因初始满管或显式禁用而自动绕行的任务；
- 至少一个因数据质量或风险信息不充分进入人工复核的任务；
- 至少一个没有可行路线而明确失败的任务；
- 至少一组“前一任务成功占用资源，后一任务被迫绕行”的可讲解链条。

验收关注覆盖类型，不要求预先固定每一类的精确数量。最终数量由同一输入和算法真实运行产生，并写入验证报告。

### 4.4 现场只讲三条代表任务

现场不逐条播放 30 个任务。建议选择：

- 任务 A：直接成功，用于说明正常流程；
- 任务 B：因前序任务占用资源而自动绕行，用于说明跨任务价值；
- 任务 C：无可行路径或数据不足，进入人工复核，用于说明系统不会伪造 PASS。

其余任务通过片区总览、任务表、统计卡片和图册页数体现规模。

## 5. 目标用户、输入与交付物

### 5.1 目标用户

- 通信线路或管道设计人员；
- GIS 数据整理人员；
- 设计复核人员；
- 项目经理或批量任务调度人员；
- 比赛中模拟上述角色的演示操作者。

### 5.2 输入

1. 批量任务表：CSV、XLSX 或 GeoPackage 非空间表；
2. 设施点图层：汇聚机房和待接入设施；
3. 候选通道图层：几何、状态、资源和相对成本；
4. 公开背景图层：道路、建筑、水体、用地、铁路；
5. 设计参数：是否优先已有通道、绕行上限、吸附阈值；
6. 显式约束：禁用路段、待核查段和任务优先级；
7. 数据清单：来源、许可证、分类、哈希和生成规则。

### 5.3 输出

- 批次运行摘要；
- 逐任务候选路线与最终路线；
- 逐任务校核历史；
- 资源预占前后快照；
- 冲突点和异常图层；
- 任务状态表；
- 片区资源利用率图层；
- 逐任务 BOM；
- 批次汇总 BOM；
- 可复算事件日志；
- 标准设计图册 PDF；
- 验证报告和产物哈希。

## 6. 目标系统工作流

### 6.1 总流程

```text
选择已审计数据集
→ 导入 30 条任务
→ 校验字段、坐标、ID 和数据版本
→ 设施点吸附到候选网络
→ 生成参数预览与批次指纹
→ 用户确认
→ 按优先级和 task_id 稳定排序
→ 为当前任务生成候选路线
→ 独立校核状态、资源和禁用约束
→ 若失败，禁用问题段并执行一次有界重规划
→ 最终 PASS 后以事务方式预占资源
→ 失败或待复核则不改变资源
→ 继续下一任务
→ 汇总任务、资源和 BOM
→ 加载 QGIS 结果图层
→ 自动生成多页图册
→ 输出日志、报告和哈希
```

### 6.2 任务状态机

```text
imported
  ↓
validated
  ↓
planned_candidate
  ↓
checked
  ├─ PASS ───────────────→ completed_direct
  ├─ 可自动修复 → replanned → PASS → completed_rerouted
  │                               └→ FAIL → needs_review / failed
  ├─ 信息不足 ───────────→ needs_review
  └─ 非法输入或无路 ─────→ failed
```

### 6.3 资源台账事务

每个批次必须从不可变的基线资源快照创建内存工作副本。每个任务遵循：

1. 读取当前剩余资源；
2. 计算候选路线；
3. 独立校核；
4. 生成待提交的资源变更集合；
5. 仅在最终 PASS 后原子提交；
6. 提交后记录 `before/after`；
7. 任务失败、异常或导出失败都不能留下半完成扣减；
8. 重跑批次时重新读取基线，避免二次扣减。

比赛版不实现多用户并发写、数据库锁、跨进程事务和生产级恢复；采用单进程、顺序、确定性执行。

## 7. 数据模型与字段语义

### 7.1 为什么必须调整容量语义

当前 `capacity_cores/used_cores` 是早期单任务样例中的简化字段，容易把“光缆纤芯数”和“管道剩余空间”混为一谈。新阶段应把通道资源和光缆规格拆开。

### 7.2 批量任务表

| 字段 | 类型 | 必填 | 含义 |
|---|---|---|---|
| `task_id` | string | 是 | 批次内唯一任务 ID |
| `batch_id` | string | 是 | 批次 ID |
| `site_id` | string | 是 | 待接入设施 ID |
| `preferred_room_id` | string | 是 | 首选汇聚机房 |
| `alternate_room_id` | string/null | 否 | 备用汇聚机房，比赛版可只记录不自动切换 |
| `priority` | enum | 是 | high/medium/low |
| `cable_fiber_cores` | integer | 是 | 新建光缆纤芯规格 |
| `prefer_existing_duct` | boolean | 是 | 是否优先候选已有通道 |
| `forbidden_asset_ids` | array/string | 否 | 显式禁用资产 |
| `required_date` | date/null | 否 | 业务说明字段，不参与首版优化 |
| `notes` | string/null | 否 | 人工备注 |

### 7.3 设施点图层

| 字段 | 含义 |
|---|---|
| `site_id` | 唯一 ID |
| `site_type` | `aggregation_room` 或 `access_site` |
| `geometry` | 点几何 |
| `node_id` | 吸附后的网络节点 |
| `snap_distance_m` | 吸附距离 |
| `data_class` | `synthetic` |
| `source_rule` | 生成或导入规则 |

### 7.4 候选通道路段

| 字段 | 含义 |
|---|---|
| `asset_id` | 唯一路段 ID |
| `from_node` / `to_node` | 拓扑端点 |
| `length_m` | 米制长度 |
| `asset_type` | 候选已有通道/合成新建段 |
| `subduct_total` | 合成子管总量 |
| `subduct_used_baseline` | 批次开始前合成已用量 |
| `subduct_reserved_batch` | 本批次新增预占量 |
| `free_subduct_count` | 当前可用量 |
| `capacity_status` | available/near_full/full/unknown |
| `segment_status` | available/forbidden/review_required |
| `cost_multiplier` | 相对成本权重，不是货币 |
| `risk_flags` | 水体、铁路、桥梁等空间提示，仅供人工复核 |
| `geometry_source` | `derived_from_public_road_geometry` |
| `business_attributes_source` | `synthetic_competition` |

### 7.5 最小容量规则

比赛版采用简单、可解释的规则：

- 每个成功接入任务沿最终路线的每一候选通道段预占 1 个子管；
- `free_subduct_count = subduct_total - subduct_used_baseline - subduct_reserved_batch`；
- 若任一路段 `free_subduct_count < 1`，则本候选路线容量校核失败；
- 光缆纤芯规格只进入任务参数和 BOM，不直接等价为子管占用数量；
- 失败、待复核任务不提交预占；
- 不实现一条子管容纳多缆、微管束、管孔组合和复杂占孔规则。

## 8. 批量规划与冲突处理算法

### 8.1 稳定排序

任务顺序固定为：

```text
priority: high → medium → low
同优先级: task_id 升序
```

排序规则写入批次摘要和图册，确保结果可复算。比赛版不允许拖拽任务后静默改变结果；如果用户改变顺序，必须产生新的参数指纹和批次 ID。

### 8.2 单任务规划

- 继续复用现有 NetworkX 确定性最短路径内核；
- 路径权重为 `length_m × cost_multiplier`；
- 不可用和已经显式禁用的路段不参与规划；
- 候选路线必须经过独立校核后才能成为最终路线；
- BOM 只能基于最终 PASS 路线生成。

### 8.3 一次有界改路

为控制开发时间，每个任务最多执行一次自动改路：

1. 第一次路线命中满管或禁用段；
2. 将本次发现的全部可禁用问题段加入本任务的临时禁用集合；
3. 重新规划一次；
4. 第二次路线独立校核；
5. 通过则完成并预占资源；
6. 仍失败则进入待人工复核或明确失败。

不实现无限循环、启发式多轮搜索和自动修改业务规则。

### 8.4 跨任务冲突

跨任务冲突只来自同一批次内的资源预占变化：

```text
T001 占用 C1-023
→ C1-023 free_subduct_count 从 1 变为 0
→ T014 的候选路线命中 C1-023
→ T014 容量校核失败
→ 禁用 C1-023 后重规划
→ 记录 caused_by_task_ids=[T001]
```

系统应能显示冲突由哪个前序任务造成。该因果链是本方案最重要的可解释性证据之一。

### 8.5 不做全局最优

本阶段明确不做：

- 多商品流全局优化；
- Steiner Tree 联合组网；
- 任务抢占和回退重排；
- 资源公平性或收益最大化；
- 并发调度；
- 自动选择所有任务的全局最优汇聚机房。

如果评委追问，应答口径为：比赛版首先解决大量重复设计的批处理和可解释冲突处理；全局优化属于后续高级优化模块，不影响当前系统替代重复劳动的价值。

## 9. QGIS 交互设计

### 9.1 页面结构

建议将现有 Dock 增加“批量设计”页签，保留单任务页签作为回归和讲解入口。

批量设计页分为五个区块：

1. **数据集区**：数据集 ID、版本、来源、校验状态；
2. **任务导入区**：选择 CSV/XLSX/GPKG、任务数、字段错误数；
3. **批次参数区**：排序规则、吸附阈值、绕行次数、已有通道偏好；
4. **执行进度区**：已完成、绕行、待复核、失败、当前任务；
5. **结果区**：任务表、地图定位、异常筛选、导出图册。

### 9.2 必须支持的交互

- 导入一批任务；
- 显示字段校验结果；
- 预览任务数量和优先级分布；
- 生成参数指纹并要求确认；
- 批量运行；
- 按状态筛选任务；
- 点击任务后缩放到该任务路线；
- 在候选路线和最终路线间切换；
- 查看资源占用前后值和冲突来源；
- 导出设计图册；
- 导出 CSV/GeoJSON/GeoPackage 结果。

### 9.3 QGIS 原生能力利用

QGIS 官方能力可以直接支撑本方案：

- Processing Batch 支持同一算法对多组输入和参数重复执行；
- Model Designer 可以把多个 GIS 步骤封装为一个可重复工作流；
- Atlas 可以按覆盖图层中的每个要素自动生成地图页；
- Print Layout 可导出单个或多个 PDF；
- GeoPackage 可以统一保存多图层和非空间表。

本项目可以通过插件控制器实现批量任务编排，并使用 QGIS Layout/Atlas 完成成册，不需要重新发明地图渲染和 PDF 引擎。

## 10. 大模型与低代码入口

### 10.1 正确定位

大模型不是路径规划器、规范裁决者或资源数据库。它只负责把用户自然语言转换为可验证的结构化草案，例如：

> “导入本周新增站点，先处理高优先级任务，优先走已有通道，禁用 C1-023 和 C2-041，冲突时只自动改路一次。”

转换为：

```json
{
  "task_source": "weekly_sites.xlsx",
  "priority_order": ["high", "medium", "low"],
  "prefer_existing_duct": true,
  "forbidden_asset_ids": ["C1-023", "C2-041"],
  "max_replans_per_task": 1
}
```

### 10.2 安全边界

- 大模型输出只能是参数草案；
- 所有 ID 必须存在于已审计数据集中；
- 所有数值必须通过 schema 校验；
- 用户必须预览并确认参数指纹；
- 大模型不能直接写资源台账；
- 大模型不能绕过校核器；
- 大模型不能把 `needs_review` 改为 `PASS`；
- 模型不可用时，结构化表单仍可完成全部核心流程。

### 10.3 实施优先级

由于比赛时间有限，大模型接口排在批量内核、数据、图册和验证之后。开发顺序应为：

```text
确定性批量内核
→ 资源台账
→ QGIS 结果与图册
→ 真实对照实验
→ 可选大模型参数入口
```

如果前四项未稳定，不应为了展示聊天效果牺牲核心交付。

## 11. 数据来源与构建方案

### 11.1 已有可复用数据

当前已审计数据位于仓库外的独立 staging 目录。其公开 GIS 背景来自 OpenStreetMap，经实际下载、敏感标签排除、几何解析、要素统计、图连通性检查和 SHA-256 校验。

已验证事实包括：

- 覆盖范围约 2.284 km²；
- 93 条道路；
- 2716 个建筑；
- 4 个水体要素；
- 50 个土地利用要素；
- 10 条铁路；
- 道路图 629 节点、667 边；
- 最大连通分量 411 节点、444 边；
- 当前 2 个站点均为合成点；
- 数据不包含真实运营商站点、管道、井位、光缆、容量、故障、成本或 BOM。

### 11.2 主展示集的数据构成

| 数据层 | 数据性质 | 构建方式 |
|---|---|---|
| 道路、建筑、水体、用地、铁路 | 真实公开 | 复用已审计 OSM 数据 |
| 候选通道几何 | 真实公开数据派生 | 使用最大连通道路图，不称现实管道 |
| 3 个汇聚机房 | 合成 | 在最大连通分量内按固定种子选择并人工复核 |
| 30 个接入设施点 | 合成 | 按建筑密度、空间分区和路网距离规则选择 |
| 子管总量、已用量 | 合成 | 使用确定性规则生成并记录种子 |
| 满管、禁用、待核查 | 合成 | 按覆盖目标选择，不能映射现实资产状态 |
| 风险提示 | 公开几何派生 + 人工复核 | 仅表示与水体/铁路等图层的空间关系，不等于规范违规 |
| 任务优先级和光缆规格 | 合成 | 通过固定任务模板生成 |

### 11.3 合成设施点生成原则

- 所有点位于最大连通分量节点或允许吸附阈值内；
- 避免真实通信设施标签和现实设施名称；
- 用规则而不是人工硬填最终路线；
- 覆盖不同路网距离、不同方向和不同汇聚机房；
- 保证地图分布可读，不把 30 个点堆在局部区域；
- 记录固定随机种子、生成脚本版本和输出哈希；
- 保留第二套不同点位的迁移验证集，用于证明系统不是只适配主场景。

### 11.4 合成资源生成原则

- 先生成不可变基线资源；
- 用 `subduct_total/subduct_used_baseline` 表示合成容量；
- 部分路段设置为接近满载，使跨任务预占能够触发后续冲突；
- 少量路段设置为初始满管或禁用；
- 禁止把公开道路的现实属性推断成地下通信资源；
- 每一合成字段在 manifest 中标注 `synthetic_competition`；
- 场景构建脚本不得根据期望最终路线直接写死 route_id 或 edge_ids。

### 11.5 可调查和可接入的数据来源

1. **OpenStreetMap/Overpass API**：获取小范围道路、建筑、水体、铁路和用地，必须保留 OSM 署名和 ODbL 信息；
2. **Geofabrik OSM extracts**：当 Overpass 不适合较大区域时，可获取省级或城市级 OSM PBF/GeoPackage，再本地裁剪；
3. **赛题组织方提供的数据**：若后续提供 QGIS 或 CAD 工程数据，应先做许可证、敏感性、坐标系、字段和拓扑审计，再通过 Adapter 接入；
4. **合法授权的学校/企业脱敏数据**：仅在得到明确授权后接入，不默认提交到公开仓库；
5. **公开规划、规范和工程文件**：只用于理解字段、流程和约束，不把其中的示意线路或设施转成现实运营商资产库。

### 11.6 不采用的数据获取方式

- 不抓取登录后或授权不明的运营商资源系统；
- 不收集真实基站精确坐标、井位、管孔占用和故障信息作为公开比赛数据；
- 不从 OSM 道路名称推断现实通信管道；
- 不把第三方网页上的施工图下载后直接作为训练或演示数据；
- 不混用 WGS84、CGCS2000、GCJ-02 和 BD-09；
- 不用未经核验的地图截图代替结构化空间数据。

### 11.7 推荐存储格式

比赛运行包建议以 GeoPackage 为主、CSV/JSON 为辅：

```text
data/competition_batch/
  manifest.json
  scenario.gpkg
    public_roads
    public_buildings
    public_water
    public_landuse
    public_railways
    candidate_channels
    facilities
    batch_tasks
    baseline_resources
  expected_coverage.json
```

GeoPackage 便于 QGIS 管理多图层和非空间表；JSON manifest 负责来源、分类、版本和哈希；CSV 只作为用户易编辑的任务入口。

### 12.1 图册建议结构

| 页码 | 内容 |
|---:|---|
| 1 | 封面、批次 ID、数据版本、非施工声明 |

### 12.2 逐任务页面必须包含

- task_id、优先级和接入设施；

## 13. 验证与指标设计

### 13.1 当前性能探针

2026-09-06 使用现有已审计最大连通图执行了只读性能探针：

- 图规模：411 节点、444 边；
- 随机固定种子任务：500 组；
- 仅执行 NetworkX 加权最短路径；
- 总耗时约 0.239948 秒；
- 平均约 0.4799 毫秒/条；
- 中位路线长度约 1084.12 米。

这个结果只证明“30 或 100 个任务的路径搜索不会成为计算瓶颈”。它不包括数据校验、动态资源、QGIS 图层、PDF、文件 I/O 和人工操作，因此不能作为比赛效率结论。

### 13.2 功能验证

必须验证：

- 30 条任务全部进入明确终态；
- 稳定排序和固定输入得到相同结果；
- 最终路线不包含禁用段；
- 任一路段资源不得出现负数；
- 失败任务不改变资源；
- 成功任务资源变更与最终路线完全对应；
- 一次绕行后仍失败时不伪造 PASS/BOM；
- 任务、路线、资源、BOM 和图册相互一致；
- 输入错误可定位到任务和字段；
- 更换设施点或容量后结果随输入真实变化；
- 第二套符合数据契约的数据可以运行。

### 13.3 端到端效率实验

人工组和系统组必须使用相同：

- 数据集；
- 任务表；
- 设计目标；
- 约束说明；
- 输出要求；
- 计算机和 QGIS 版本；
- 起始状态和结束条件。

统一起点：操作者拿到任务表和数据包。
统一终点：完成片区总览、逐任务图纸、汇总表和异常清单。

记录指标：

- 端到端历时；
- 人工主动操作时间；
- 鼠标/键盘有效操作数；
- 完成任务数；
- 规则漏检和误判；
- 返工次数；
- 图册完整率；
- 异常识别准确率；
- 输出与资源台账一致性。

主指标：

```text
效率提升率 = (人工端到端时间 - 系统端到端时间) / 人工端到端时间 × 100%

操作减少率 = (人工有效操作数 - 系统有效操作数) / 人工有效操作数 × 100%
```

在人工基线真实完成之前，报告只能写 `pending_human_baseline`，不得提前声称达到 30% 或 50% 门槛。

### 13.4 人工实验规模

最可信方案是由至少 1 名操作者完整完成同一批 30 个任务的人工流程和系统流程，并全程录屏。如果比赛时间不足，可以采用分层方案：

- 10 个具有代表性的任务完成完整人工对照；
- 30 个任务完成系统批量运行和图册生成；
- 明确报告人工基线只覆盖 10 个任务；
- 不把 10 个任务的时间线性外推成 30 个任务结论。

### 13.5 非写死验证

至少完成以下三种反证：

1. 移动一个合成设施点，路线和图纸随之变化；
2. 将一个路段剩余子管从 1 改为 0，后序任务出现绕行或失败；
3. 导入第二套 10 任务迁移验证集，不修改算法代码即可运行。

这比口头宣称“没有写死”更有说服力。

## 17. 风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 30 个任务只是机械循环 | 创新和价值不足 | 保留跨任务资源预占和因果链 |
| 共享资源实现过于复杂 | 延误 | 单进程、固定排序、成功后预占、一次改路、不抢占 |
| 容量概念错误 | 被专业评委质疑 | 拆分子管容量与光缆纤芯规格 |

| 图册只有重复地图 | 工程意义弱 | 每页包含参数、冲突、资源前后值、BOM 和指纹 |
| QGIS Atlas 页面乱码或重叠 | 展示失败 | 导出后重读、全页渲染、人工目视 |
| 系统效率指标边界不一致 | 指标无效 | 人工和系统使用相同起点、终点和交付物 |
| 大模型产生幻觉参数 | 错误执行 | 模型只生成草案，schema + 指纹 + 用户确认 |
| 新数据下载失败或含敏感标签 | 延误/合规风险 | 优先复用已审计数据；扩区作为可选项 |
| 截止日前需求继续扩张 | 核心不稳定 | 09-14 前冻结，不加入无线仿真、CAD、造价和云平台 |

## 20. 评委追问口径

### 20.1 “2.3 平方公里是不是太小？”

> 这是核心城区样板片区，不是全国规模压测。当前公开背景已有 2716 个建筑、411 个连通节点和 444 条候选路段。设计工作量由 30 条任务、资源共享、冲突返工和约 36 页交付物构成。我们另外用 100 条任务做压力测试，并通过同一数据契约证明可以替换为更大区域。

### 20.2 “是不是把一个算法运行了 30 次？”

> 批量重复本身就是要解决的行业劳动，但系统不是 30 次互不相关的调用。前一任务成功后会预占路段资源，后续任务读取更新状态，可能因此改路或失败；每个冲突都能追溯到前序任务和资源变更。

### 20.3 “数据是不是真实的？”

> 道路、建筑、水体、铁路和用地是经过来源、敏感性、几何、拓扑和哈希审计的公开 GIS 数据。设施点、候选通道身份、子管容量和业务状态是明确标注的合成竞赛数据。我们证明的是流程可运行和数据可替换，不冒充已经接入运营商现网。

### 20.4 “是不是写死的？”

> 路线没有写入场景答案。系统根据导入任务、网络、容量和禁用约束实时计算。现场改变一个站点或一段容量，后续路线、冲突、BOM 和图册都会改变；第二套任务集也可以不改代码运行。

### 20.5 “大模型有什么作用？”

> 大模型降低参数表达门槛，把自然语言转换为结构化任务草案；确定性的路线、资源、校核和制图内核负责工程结果。模型不能修改资源、跳过校核或自行宣布 PASS。即使模型不可用，表单和批量任务表仍能完成全部核心流程。

### 20.6 “为什么不用 Codex 或通用 GPT 直接做？”

> 通用模型可以协助写代码和理解意图，但它没有经过版本控制的项目数据、资源事务、可复算路线内核、QGIS 图层生命周期、规则证据和标准化交付链。本系统把模型放在低风险交互层，把工程决策固化为可验证、可重复、可审计的软件流程。
